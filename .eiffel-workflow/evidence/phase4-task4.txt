[DONE] `itemize' runs AnalyzeScript over the span and takes the INTERSECTION
       with the bidi levels.
       The SCRIPT half is asked of DirectWrite per call, through
       DWRITE_API.analyze over the span's UTF-16 buffer, and read back as one
       run index per CODE POINT.
       The BIDI half is NOT re-asked of DirectWrite: it is read out of the
       `a_bidi' the facade already resolved through seam 1. That is the oracle,
       not a shortcut - `one_level_per_item' is checked against THAT
       BIDI_RESULT, so splitting on any other level table could satisfy
       DirectWrite and still violate the seam. (DWRITE_API.analyze does refill
       the shim's bidi run table as a side effect; this class ignores it.)
       SPLIT RULE: a new item begins wherever the opaque SCRIPT ID changes or
       the LEVEL changes. Splitting on the run INDEX would be a defect:
       DirectWrite may deliver two adjacent runs carrying the same script id,
       and a boundary with neither a script-id change nor a level change
       violates `boundaries_are_script_or_bidi'. An item's analysis bytes come
       from the run covering its FIRST code point.
       MEASURED, this run - the intersection's necessity, reproduced:
         D-015 raw     : 3 AnalyzeScript runs, 2 AnalyzeBidi runs
         D-015 itemized: 4 items

[DONE] Positions are CODE-POINT space; the UTF-16 mapping is owned here.
       Owned exactly as Task 3 owns it in DIRECTWRITE_BIDI_RESOLVER, and now
       FACTORED into the new class DIRECTWRITE_UTF16_MAPPING, which
       DIRECTWRITE_SCRIPT_ITEMIZER inherits. Three steps, the same every time:
         1. `first_units' records, per code point, the 0-BASED index of its
            FIRST UTF-16 unit (a code point above U+FFFF takes two);
         2. `utf16_span' fills the buffer, surrogate halves hand-built at those
            offsets;
         3. the caller spreads what the shim reports over a per-UNIT array and
            reads ONE answer per CODE POINT at its first unit.
       WHICH OPTION WAS TAKEN, as the brief asks: a SHARED {NONE} HELPER CLASS
       was factored - not a duplicate. Task 3's DIRECTWRITE_BIDI_RESOLVER was
       deliberately NOT rewritten onto it: it is a merged, contract-frozen file
       and Task 4 does not refactor one. Its private copy of steps 1 and 2
       (inside `resolved_levels' and `probe_level') therefore still stands;
       rebasing it is a mechanical, behavior-free change for a later pass, and
       both the helper class note and the itemizer note say so.

[DONE] Each item carries ONE opaque script id and ONE level, and its `analysis'

[DONE] Native failure path degrades per NFR-011, never raises.
       The documented fallback for `itemize' is the LEVEL-SPLIT answer: items
       split at bidi level changes alone, ONE opaque script id 0, empty
       analysis bytes - i.e. the Phase-1 body, which is a lawful intersection
       (adjacent items then always differ in level) and the same shape
       NULL_SCRIPT_ITEMIZER produces, so a headless machine degrades to
       headless behavior. It is taken when `backend_open' is False (dwrite.dll
       missing, or factory/analyzer creation failed) and when `analyze' returns
       False; `span_script_runs' answers -1 for every code point in either
       case, and -1 means "no run", which `script_id_at' turns into id 0 and
       `analysis_of_run' into empty bytes. No partial truth is ever emitted.
       `soft_breaks' degrades the same way to "a break after an ASCII space",
       which is NULL_SCRIPT_ITEMIZER's rule.
       Both features additionally carry a rescue that takes that fallback ONCE
       and only once (the rescue re-raises on a second failure rather than
       looping), so no exception can cross the seam. The class note and the
       class-level `never_raises' tag both say all of this.

       CAN_BREAK (1) and MUST_BREAK (3) count as opportunities; NEUTRAL (0) and
