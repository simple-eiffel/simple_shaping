DESIGN NOTES FOR TASK 8 (why the API has this shape)
  * Keys are CANONICAL: VS16 is dropped before lookup, exactly as
    EMOJI_ASSET_CATALOG.asset_key drops it. So "2764 FE0F" and "2764" answer the
    same, a fully-qualified keycap and a minimally-qualified one both match, and
    a matched sequence maps one-for-one onto the asset name the catalog will
    probe. Task 8's rung 1 is therefore
        n := tables.longest_rgi_prefix_length (text, i)
        if n > 0 and catalog.has_asset (tables.codepoints_of (text, i, n)) then ...
  * longest_rgi_prefix_length is deliberately NOT gated on is_emoji_starter:
    keycap bases ('#', '*', '0'..'9') are Emoji_Component, NOT
    Extended_Pictographic, yet they start RGI keycap sequences. Gating the scan
    on is_emoji_starter would lose all twelve keycaps - and is_emoji_starter's
    `definition' ensure is frozen, so the fix had to live here, not there.
  * The set is exactly RGI (emoji-test.txt `fully-qualified', unioned with
    emoji-zwj-sequences.txt). A bare Extended_Pictographic character that is
    only ever listed as `unqualified' (a lone U+2764 with no VS16) therefore
    yields 0 from the longest match. That is correct and it is NOT a hole: the
    segmenter's existing single-codepoint rung -
    has_resolvable_single / no_resolvable_single_left_plain - is what lifts
    those, and emoji_u2764.png exists so it will.
  * Both lookup structures are per-object self-initializing attributes, not
    `once' data: EMOJI_DATA_TABLES is owned by the facade (SCRIPT_ITEMIZER's
    emoji_tables_ownership note, ISSUE 19), one instance per processor, so there
    is no shared mutable state and nothing to synchronize under SCOOP.
  * is_extended_pictographic allocates NOTHING per call (binary search over the
    already-built range list) because it is evaluated inside
    is_emoji_starter's postcondition.
