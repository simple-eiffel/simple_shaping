THE HFONT-LIFETIME DECISION, AS IMPLEMENTED
-------------------------------------------
THE DEFECT (simple_cairo 1.3.0's own CAIRO_FONT_FACE note, measured there):
cairo's win32 font-face hash table is keyed on FACE NAME, WEIGHT and ITALIC. It
ignores both the height and the HFONT. So the face cairo builds from an HFONT
outlives every CAIRO_FONT_FACE object wrapping it and is handed back for every
later HFONT of the same family. DeleteObject on an HFONT cairo has seen leaves
cairo holding a dangling GDI handle; the next paint through it fails with
CAIRO_STATUS_WIN32_GDI_ERROR (41), which poisons that context AND the shared
face for the rest of the PROCESS - including fonts that never touched this one.

THE DECISION: a SHAPING_FONT that has handed its HFONT to cairo NEVER deletes
that HFONT. Its GDI chain becomes process-lifetime.

AS IMPLEMENTED, in SHAPING_FONT.dispose (body only):
  1. l_cairo_holds_the_hfont := has_cairo_face      -- asked BEFORE anything is
                                                    -- dropped
  2. internal_cairo_face.destroy                    -- drop OUR reference only
  3. internal_cairo_face := Void ; has_cairo_face := False
  4. IDWriteFontFace Release                        -- unchanged
  5. restore the DC's original font                 -- unchanged
  6. if l_cairo_holds_the_hfont then
         release_gdi_chain (..., a_font := default_pointer)   -- NO DeleteObject
     else
         release_gdi_chain (..., a_font := font_handle)       -- as before
     end
     -- the DC is restored and DeleteDC'd on BOTH paths; only the HFONT is
     -- left alive, on purpose.
  7. font_handle := default_pointer                 -- unchanged, so
                                                    -- handles_released still
                                                    -- holds

COST: one GDI font object per (family, weight, italic, size) EVER PAINTED, for
the life of the process. Bounded by the identity space a FONT_REGISTRY hands
out - for a chat client, a handful. A font that never painted still deletes its
HFONT normally, so nothing regressed for the 60 pre-existing tests, several of
which realize and dispose Segoe UI without ever asking for a face.

CONTRACTS: dispose's ensure clauses are UNCHANGED and all still hold -
  unrealized / no_cairo_face / handles_released / metrics_cleared /
  realizable_again / identity_kept. handles_released says font_handle =
  default_pointer, which is about the ATTRIBUTE, and the attribute is still
  cleared; the GDI object behind it is what is deliberately leaked.

DOCUMENTED IN: SHAPING_FONT's class note (a new "PHASE 4 TASK 13 - THE FACE IS
REAL, AND IT COSTS AN HFONT FOREVER" section), cairo_face's own header comment
("ASKING THIS QUESTION COMMITS THE HFONT FOR THE LIFE OF THE PROCESS"), the
inline comment at the branch in dispose, and CHANGELOG [Unreleased].
FONT_REGISTRY's note already told the reader that this class owns native
lifetime and that dispose_all runs SHAPING_FONT.dispose; the rule that dispose
now enforces is stated where the decision is made and where a maintainer will
be standing when they wonder why an HFONT is not freed.

TESTED AS BEHAVIOR, not as a comment:
test_cairo_face_is_lazy_and_disposal_leaves_the_process_healthy realizes Segoe

A SECOND SUPPLIER DEFECT FOUND AND CONTAINED (not in the brief)
---------------------------------------------------------------
cairo_image_surface_create_from_png answers a FAILED load with a static ERROR
surface: a NON-NULL handle whose status is non-zero. CAIRO_SURFACE's own
invariant is

    destroyed_implies_null: not is_valid implies handle = default_pointer

so such a surface violates its class invariant the instant it leaves
make_from_png, and every qualified call on it - is_valid and destroy INCLUDED -
raises as well. A cache that simply asked "did it decode?" would therefore raise
on a missing asset, which is exactly what NFR-011 forbids below the facade.

CONTAINED, two defenses, both documented in EMOJI_SURFACE_CACHE's class note:
  1. is_readable_file gate - the ORDINARY miss (an asset that is simply not
     there) never reaches cairo's loader at all.
  2. surface's rescue/retry - a present-but-corrupt PNG raises inside the
     supplier; the rescue counts one failure, answers Void, and lets a SECOND
     failure propagate rather than spin.
An error surface is never destroyed here: cairo's is static, there is nothing to
free, and the attempt would itself raise.
This is a simple_cairo observation, NOT a simple_cairo change - that repo was
not touched. It is worth a line in simple_cairo's own backlog: make_from_png
could null its handle on a failed load, or expose a make_from_png_if_readable.

FOR TASK 11 - THE EXACT API THE FACADE MUST CALL TO PAINT
----------------------------------------------------------
  Nothing in src/simple_shaping.e was touched. Wire it like this:

    local
        bridge: SHAPING_CAIRO_BRIDGE
    ...
    create bridge.make                      -- owns its own EMOJI_SURFACE_CACHE
    -- or, to share one cache across panes on the processor:
    create bridge.make_with_cache (my_cache)

    bridge.draw_layout (a_context, a_layout, a_x, a_y)
        require  a_context.is_valid
        -- (a_x, a_y) is the layout's TOP-LEFT corner. Lines stack by their own
        -- heights; each line's baseline is its top plus its ascent.

    bridge.draw_line (a_context, a_line, a_x, a_baseline_y)
        require  a_context.is_valid
        -- for a facade that owns its own line loop; a_baseline_y is a BASELINE,
        -- not a top.

  After a paint, read: bridge.painted_runs, bridge.skipped_runs,
  bridge.last_skip_note; bridge.reset_counters clears them;
  bridge.run_count (layout) says how many runs a layout will visit;
  bridge.surfaces.dispose_all releases the decoded emoji at facade teardown.

  IF A FACADE CONVENIENCE IS WANTED, it is three lines and it belongs in Task
  11's own edit of src/simple_shaping.e:

      paint (a_context: CAIRO_CONTEXT; a_layout: SHAPED_LAYOUT; a_x, a_y: REAL_64)
          require context_valid: a_context.is_valid
          do bridge.draw_layout (a_context, a_layout, a_x, a_y) end
          ensure context_survives: a_context.is_valid

  WHAT TASK 11 OWES THE BRIDGE, and it is the one thing a facade can get wrong:
  GLYPH_RUN.x_positions / y_positions are POSITIONS, not the shaper's advances
  and not its offsets. Fold them:

      x_positions [i] = sum of shaped.advances [1 .. i-1] + shaped.x_offsets [i]
      y_positions [i] = -shaped.y_offsets [i]

  The NEGATION is not optional. DirectWrite's DWRITE_GLYPH_OFFSET.ascenderOffset
  is positive UPWARD; cairo's user space is y-down. The bridge adds
  y_positions [i] to the baseline and does not interpret it, which is the
  correct layering - but it means the sign is the assembler's to get right.
  testing/lib_tests.e's glyph_run_from does exactly this fold and is the
  reference; Task 10's headless_glyph_run passes shaped.x_offsets straight
  through as positions, which is fine for a NULL shaper whose offsets are all
  zero and is NOT the production rule.
