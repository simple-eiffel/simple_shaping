  two Task 3 named, with counts; anything new = FAIL with the first mismatches
  printed." The full run found something NEW, so this is reported at the top of
  the report rather than absorbed.

  CLASS 1 - paired brackets (rule N0 / BD16)          5,292 (character file)
  CLASS 2 - explicit directional formatting         244,001 (39 + 243,962)
  CLASS 3 - rule L1 around a SEGMENT SEPARATOR          217 (class file)  <- NEW

  CLASS 3, WORKED. UAX #9 L1 resets a segment separator itself, and any
  WHITESPACE or isolate formatting characters PRECEDING it, to the paragraph
  level - and nothing else. AnalyzeBidi also resets the NON-whitespace neutrals
  that flank one:
      R S ET AL   ; LTR    Unicode 1 0 1 1    DWrite 1 0 0 1
      R ES S AL   ; LTR    Unicode 1 1 0 1    DWrite 1 0 0 1
      AN S ET AL  ; LTR    Unicode 2 0 1 1    DWrite 2 0 0 1
  All 217 have that shape. It needs a TAB (U+0009), U+000B or U+001F immediately
  beside a neutral. BidiCharacterTest.txt produced ZERO cases of this class in
  its 91,707 - it barely uses TAB, and Task 3's sample used none - which is why
  only the class file could find it.

  WHAT WAS DONE ABOUT IT, and why. Not hidden, not made to pass:
    * the class is NAMED, counted separately, printed with worked examples, and
      documented in `LIB_TESTS.has_segment_separator', tools/bidi-conformance.md,
      the CHANGELOG and the README;

      `assert_integers_equal ("no UNCLASSIFIED conformance mismatch - a NEW

      divergent run is a SKIP naming the classes and their counts (the Task-3

  Widening the classification rather than leaving the suite permanently red is a
